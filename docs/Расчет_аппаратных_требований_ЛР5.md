# Расчет аппаратных требований и емкости дискового пространства

## Тема проекта
**«Оптимизатор запросов баз данных (Database Query Optimizer)»**  
Предметная область: Веб-сервис для анализа, подбора и тестирования конфигураций индексов в реляционной СУБД PostgreSQL (типы: B-Tree, BRIN, Hash, GIN, GiST).

---

## 1. Исходные параметры нагрузки и пользователей

1. **Количество активных пользователей ($N_{users}$):**
   $$N_{users} = 1\,500 \text{ инженеров/разработчиков}$$
2. **Рабочее время пользователей в день ($T_{work}$):**
   $$T_{work} = 8 \text{ часов} = 8 \times 3\,600 = 28\,800 \text{ секунд}$$
3. **Количество услуг (индексов), просматриваемых / создаваемых одним пользователем в день ($N_{services}$):**
   $$N_{services} = 30 \text{ услуг/день}$$
4. **Количество HTTP-запросов на обработку одной услуги ($N_{http}$):**
   Для полного цикла работы с одной услугой (загрузка списка с фильтрацией, получение деталей, загрузка медиа MinIO, проверка сессии):
   $$N_{http} = 4 \text{ запроса (GET /api/indexes, GET /api/indexes/:id, GET /uploads/..., GET /api/auth/me)}$$

---

## 2. Расчет сетевой нагрузки и RPS (Requests Per Second)

### 2.1. Средний показатель RPS ($RPS_{avg}$):
$$RPS_{avg} = \frac{N_{users} \times N_{services} \times N_{http}}{T_{work}} = \frac{1\,500 \times 30 \times 4}{28\,800} = \frac{180\,000}{28\,800} = 6.25 \text{ зап/сек}$$

### 2.2. Пиковый показатель RPS ($RPS_{peak}$):
С учетом коэффициента пиковой неравномерности $k_{peak} = 3.5$ в часы наивысшей активности разработчиков:
$$RPS_{peak} = RPS_{avg} \times k_{peak} = 6.25 \times 3.5 = 21.875 \approx 22 \text{ зап/сек}$$

---

## 3. Расчет аппаратных требований к вычислительным ресурсам сервера

По методическим указаниям:
* На одно процессорное ядро (vCPU) сервера приложений и БД выделяется **по 4 ГБ оперативной памяти (RAM)**.
* Одно процессорное ядро веб-сервера (NestJS / Node.js) способно стабильно обрабатывать до 15-20 сложных аналитических запросов в секунду с обращением к БД.

### 3.1. Расчет количества ядер процессора ($N_{cpu}$):
$$N_{cpu} = \left\lceil \frac{RPS_{peak}}{RPS_{core}} \right\rceil + N_{reserve} = \left\lceil \frac{22}{15} \right\rceil + 2 = 2 + 2 = 4 \text{ ядра (vCPU)}$$
*(где $N_{reserve} = 2$ — резерв для фоновых задач СУБД, кэша Redis и сборщика мусора V8).*

### 3.2. Расчет объема оперативной памяти ($V_{RAM}$):
Исходя из нормативного соотношения **4 ГБ ОП на 1 процессорное ядро**:
$$V_{RAM} = N_{cpu} \times 4 \text{ ГБ} = 4 \times 4 \text{ ГБ} = 16 \text{ ГБ RAM}$$

---

## 4. Расчет размера одной записи в таблицах БД (Спецификация полей в байтах)

В базе данных PostgreSQL хранятся две основные сущности: пользователи (`users`) и оптимизированные индексы (`database_indexes`).

### 4.1. Таблица `database_indexes` (Услуги):

| Поле | Тип данных в PostgreSQL | Размер поля в байтах |
| :--- | :--- | :--- |
| `id` | `INT` / `SERIAL` (PK) | 4 байта |
| `index_name` | `VARCHAR(255)` (средняя длина 40 символов) | $40 + 1 = 41$ байт |
| `table_name` | `VARCHAR(100)` (средняя длина 20 символов) | $20 + 1 = 21$ байт |
| `index_type` | `VARCHAR(50)` (B-Tree, BRIN, Hash, GIN) | $6 + 1 = 7$ байт |
| `column_name` | `VARCHAR(100)` (средняя длина 20 символов) | $20 + 1 = 21$ байт |
| `cardinality` | `INT` | 4 байта |
| `estimated_creation_time_sec` | `INT` | 4 байта |
| `short_description` | `TEXT` (средняя длина 120 символов) | $120 + 4 = 124$ байта |
| `full_description` | `TEXT` (средняя длина 800 символов) | $800 + 4 = 804$ байта |
| `status` | `VARCHAR(50)` ('published', 'draft', 'deleted') | $9 + 1 = 10$ байт |
| `likes_count` | `INT` | 4 байта |
| `image_url` | `VARCHAR(500)` (средняя длина 70 символов) | $70 + 1 = 71$ байт |
| `video_url` | `VARCHAR(500)` (средняя длина 70 символов) | $70 + 1 = 71$ байт |
| `author_id` | `INT` (FK) | 4 байта |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | 8 байт |
| **Служебный заголовок строки** | HeapTupleHeader в PostgreSQL | 24 байта |
| **Указатель в листовой странице** | ItemId (Line pointer) | 4 байта |

**Итого средний размер одной строки услуги в БД ($S_{row}$):**
$$S_{row} = 4 + 41 + 21 + 7 + 21 + 4 + 4 + 124 + 804 + 10 + 4 + 71 + 71 + 4 + 8 + 24 + 4 = 1\,222 \text{ байта} \approx 1.2 \text{ КБ}$$

### 4.2. Медиафайлы в хранилище MinIO на одну услугу ($S_{media}$):
* Скриншот плана запроса (PNG/JPEG): в среднем $350 \text{ КБ}$
* Видеодемонстрация оптимизации (MP4): в среднем $4.5 \text{ МБ} = 4\,608 \text{ КБ}$
$$S_{media} = 350 + 4\,608 = 4\,958 \text{ КБ} \approx 4.84 \text{ МБ}$$

---

## 5. Расчет требуемого размера жесткого диска с учетом прироста за 5 лет

Пусть в год создается $N_{annual} = 12\,000$ новых конфигураций индексов (услуг).  
За $T_{years} = 5$ лет общее количество добавленных услуг составит:
$$N_{total} = N_{annual} \times T_{years} = 12\,000 \times 5 = 60\,000 \text{ записей}$$

### 5.1. Прирост данных реляционной СУБД (PostgreSQL):
С учетом накладных расходов на индексы первичных и внешних ключей ($k_{idx} = 1.4$) и коэффициент фрагментации/журналов WAL ($k_{wal} = 1.3$):
$$V_{DB} = N_{total} \times S_{row} \times k_{idx} \times k_{wal}$$
$$V_{DB} = 60\,000 \times 1\,222 \text{ байт} \times 1.4 \times 1.3 = 133\,442\,400 \text{ байт} \approx 0.133 \text{ ГБ}$$

### 5.2. Прирост объектного хранилища медиаданных (MinIO):
$$V_{media} = N_{total} \times S_{media} = 60\,000 \times 4.84 \text{ МБ} = 290\,400 \text{ МБ} \approx 283.6 \text{ ГБ}$$

### 5.3. Резервное копирование и системный раздел:
* Ежедневные/еженедельные бэкапы (глубина хранения 3 копии): $V_{backup} = 284 \text{ ГБ} \times 1.5 = 426 \text{ ГБ}$
* ОС, системные логи, Docker-образы: $50 \text{ ГБ}$

### 5.4. Итоговая требуемая емкость диска ($V_{disk}$):
$$V_{disk} = V_{DB} + V_{media} + V_{backup} + V_{OS} = 0.133 + 283.6 + 426 + 50 = 759.733 \text{ ГБ}$$

С округлением до стандартного серверного накопителя (с запасом 25% на нештатное масштабирование):
**Рекомендуемый объем NVMe SSD: 1 000 ГБ (1 ТБ)**.

---

## 6. Итоговая конфигурация сервера (Спецификация)

* **Процессор:** 4 ядра vCPU (базовая частота $\ge 2.8$ ГГц)
* **Оперативная память:** 16 ГБ RAM (ECC DDR4 / DDR5)
* **Дисковая подсистема:** 1 ТБ NVMe SSD (RAID-1 зеркалирование для отказоустойчивости)
* **Сетевой интерфейс:** 1 Гбит/с
