- Открыть отчёт, React на `http://127.0.0.1:5188/`, релизную `Index Catalog.app` и заранее настроенные запросы Insomnia. Для живого показа нужны NestJS, PostgreSQL, Redis, объектное хранилище и Asyncio.
- Проверить, что `.app` загружает каталог. В проверенном релизе API — `http://192.168.1.78:3108`, медиа — `http://192.168.1.78:9018`. Если LAN IP сменился, пересобрать приложение с новым адресом.
- Подготовить локальный JPEG [`index_users_email.jpg`](../../database_query_optimizer/public/media/index_users_email.jpg). Ключ callback оставить в приватном окружении Insomnia; не показывать его, значения cookies или подписанные URL.

## 1. Индексы, пагинация и Redis (+4)

1. Открыть `http://127.0.0.1:5188/?cardinality=420042`. Показать 750 совпадений, разные наборы записей на страницах 1 и 2, затем страницу 32: позиции 745–750 (рис. 1–2).
2. Показать сохранённые замеры из §1.1 отчёта. Составной B-tree `(status, cardinality, id)` поддерживает фильтр и сортировку. Медиана `Execution Time` запроса страницы — 0,082 мс с индексом и 1,740 мс без него. Это время запроса PostgreSQL, не задержка HTTP. Живое удаление индекса не требуется.
3. По §1.3 показать результат прогона Redis: в партии гостя 100 уникальных ID, переход 100 → 1 создаёт новую партию, вошедший получает отдельную. Опрос по ID не двигает курсор.

## 2. Нативное приложение и CLIP (+3)

1. В релизной `.app` показать LAN-адрес и гостевой режим. Выбрать BRIN, применить фильтр (24 004 результата), открыть `idx_orders_created_at` и показать детали с изображением (рис. 3–4).
2. Вернуться в каталог: **Поиск по изображению → Выбрать файл → Найти совпадения**. Выбрать JPEG через системный диалог, не встроенный пример. Порог — 0,65, TopK — 1. В проверенном прогоне: 14 описаний, одно совпадение **№120016**, сходство **0,664**, косинус **0,328**. Открыть `demo_clip_card_cabinet` из результата (рис. 5–7). Фото обрабатывается на устройстве; сходство не является вероятностью.
3. Показать `idx_users_email` до и после повторного открытия после смены `full_description` (рис. 8–9). При живом повторе работать только в отдельной учебной БД `dz_extras`: сохранить исходный текст, добавить маркер, показать карточку, восстановить текст и проверить через API.
4. По §2.2 показать соединение релизного процесса с `192.168.1.78:3108` в состоянии `ESTABLISHED`. Источник — `netstat`; свежего пакетного захвата нет.

## 3. GLB, Asyncio и Short Polling (+3)

1. Показать форму загрузки GLB и опубликованную модель (рис. 10). Открыть `http://127.0.0.1:5188/feed?next=true`, не нажимать «Далее» повторно. Через 6–8 секунд показать поворот модели на той же карточке (рис. 11).
2. В Insomnia: `GET /api/indexes/feed` → `GET /api/indexes/feed?next=true` → немедленный `GET /api/indexes/feed?id=<ID>` с ID из ответа. Повторить последний запрос после задержки. Позиция и ID не меняются, углы отличаются (рис. 12–14). React опрашивает тот же ID примерно каждые 1,5 с; Asyncio вычисляет углы, NestJS сохраняет их.
3. Отдельный пример: `POST http://127.0.0.1:8108/rotate` с `{"id":120020,"rotationX":0.5,"rotationY":1.0}`. Показать `202 Accepted`. После задержки GET через NestJS по ID 120020 покажет примерно 0,948799 и 2,047198 рад (рис. 15–16).
4. После завершения задачи отправить ручной `PUT /api/indexes/120020/rotation` с углами 0,6 и 1,2 рад. Неверный ключ даёт `401`, правильный — `204`. Контрольный GET подтверждает 0,6 и 1,2 рад (рис. 17–18).
